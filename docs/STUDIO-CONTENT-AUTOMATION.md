# 小影匠定时内容增长设计

2026-11-28 · 实施规格。内容增长服务两件事，让已有作品的创作者看到海外市场机会，也看到做相近内容的人取得的结果与可核对收益。首批以 YouTube 知识解说、动画和财经解说为范围。文章模板与证据口径沿用 [手册编辑规格](STUDIO-EDITORIAL.md)。

## 调度和产出

保留原任务的北京时间周一、周四 08:30。新工作流使用同一条 UTC cron `30 0 * * 1,4`，每次都采集并处理到期队列，按轮次优先处理不同栏目。GitHub 的 schedule 可能延迟或丢弃一次触发，采集从各来源上次成功位置继续，下一轮可补漏。手动入口可仅采集、预演或补跑已登记的题目 ID。[GitHub 定时触发说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

| 轮次 | 定时从哪里拿什么 | 优先产出 |
| --- | --- | --- |
| 周一 08:30 | YouTube 官方 RSS、新报告及已登记的功能与变现说明，抽取公告时间、适用地区或语种、数据窗口和有出处的结果。并采集频道与作者站变化。 | 一篇题材市场观察，或将可比的新报告补进旧市场页。 |
| 周四 08:30 | 同一批平台、频道和作者站。重点提取新作品的原链接和发布时间、作者披露的增长或收益、扩语种或推出产品的节点。 | 一篇有完整证据的成功案例，或更新已发布的案例时间线。 |
| 每月第一轮周一 | 同一次运行比较各来源的成功率、最近可用证据、待补证条目及实际搜索查询。已获批准的原始来源可以试采，开放搜索发现的新域名先列为候选。 | 更新关注清单与后续选题，产生内部报告。可用市场证据照常排队。 |

启动阶段每次定时可以采完来源并更新队列，最多交付一个合格的文章单元。证据不足时可选另一栏的就绪题、已积累的常青题，或仅记录待补证。增加来源和成稿上限以真实通过率与成本为依据。预算暂沿用旧工作流每批最多 15 次模型调用和 100,000 个保守 Token，首版通过受信配置设更低运行上限也不改变预算上限。每轮报告列出采集、去重、跳过、入队、核验、发布和失败状态。

信号和证据在入队时区分。频道新视频、搜索结果和 RSS 摘要是找资料的线索。原报告段落、作者披露或原始作品才进入可用于写稿的证据包。媒体处于不可读取状态时记录链接和待补证原因，允许人提供原始出处及时间点，以后仍走同一独立核验。来源接入读取公开允许的页面、订阅或接口；YouTube API 数据的存储、刷新和衍生用途需符合其条款。首版用官方频道订阅做发现，正文的长期数值证据以可引用报告和作者披露为主。[YouTube API 开发者政策](https://developers.google.com/youtube/terms/developer-policies)

## 怎样稳定产生新稿与旧文更新

1. **每轮增量采集。** 来源配置记录类型、规范链接、对应题材与要读取的范围。采集器记录观察日期、原始 ID、规范链接、发布时间和相关内容指纹。支持上游提供的 ETag 或 Last-Modified，并复查近期条目以补漏。首次导入的已找到原始资料进入常青队列。对同一证据稳定去重，文章页面改标题也保持身份。
2. **按读者问题入队。** 一条新报告命中已存在的问题就更新原页。提出不同读者问题且有实质证据时，才新增文章。案例就绪至少要有可核对的结果和发展节点，并写出一项对国内同类创作者有用的启示。收益金额、占比须有出处、窗口、币种及范围。新作品可以给已存在案例补样本，有实际节点才能形成更新。没有新公告时，从已积累的证据里选同题材对照或补齐待写案例。
3. **分开事实、比较与判断。** 证据包记录主张、来源、原文位置、观察日和能支持的范围。写作任务输出 Markdown 正文、可见摘要、证据引用及推荐内链。独立核验逐条看数据口径、比较是否成立、对读者增加了什么，以及是否和现有文章意图重叠。结构化程序检查来源、允许文件、稳定地址和三个产物的一致性。
4. **扩充题库。** 每篇文章登记后续要观察的一项变化，例如报告下一期、创作者首个公开赞助披露、进入新语种或发布自有产品。加入已可读的同题材作者和已发布市场页的相邻问题。新发现的来源和待用证据进入候选队列，由受信配置确定是否长期采集。规模随可用来源和通过核验的选题扩大。

| 发现的变化 | 怎样产出 |
| --- | --- |
| YouTube 发了新一期可比的多语观看数据 | 更新原「知识解说多语触达」页面，保留旧数据的历史口径和来源。 |
| Kurzgesagt 发表新一期有明确日期和统计范围的收入披露 | 更新既有团队案例的收入部分及时间线；由独立核验检查新旧范围能否比较。 |
| 同题材另一个团队有公开的起点、商业节点和结果 | 有独立问题时写新案例，并链接相关市场观察。 |
| 本轮只有常规上传、重复报道或不支持结论的证据 | 刷新来源和候选队列，已有证据充足的题照常产出。其余候选等进一步资料。 |

## 沿用现有发布机制

旧 `.github/retired-workflows/upstream.yml` 仅作实现参考。它带有 HyperFrames 专用知识盘点、生成命令和文章注册表。新建工作室内容工作流，复用固定 main SHA、并发保护、独立核验、受信 PR、准确提交部署和 Cloudflare 恢复。现有发布与内容守卫目前仍有旧知识数据依赖。实现时让新文章有可管控的验证摘要和发布失败标记，复用检查与恢复逻辑，避免失败的文章原样进入后续部署。

- 待办、来源游标、重试日期和证据去重键持久化到专用状态分支，状态提交不触发生产部署。状态分支只保存可公开链接和运行元数据，不写受限原文、合作材料或密钥。可复用的文章依据和已发布的证据基线随批准后的内容单元提交。新运行先核对 main 与线上清单，恢复上次合并或发布未写完的状态。
- 正文 `src/content/creators/<slug>.md`、来源与栏目 `content/creator-guides.json`、问题与可见摘要 `content/discovery.json` 一起检查和落盘。市场与案例栏目须先加入受信站点注册与校验。生成器只提议正文、摘要和证据引用。来源基线、已有地址与日期由规则校验后推进。
- 仅有状态变化的批次不创建内容 PR。合格文章提交依次运行 `pnpm check`、`pnpm test`、`pnpm build`、`pnpm test:indexing`、`pnpm test:e2e`。使用独立的内容任务权限，外部 PR 的检查继续只读。校验准确 PR HEAD 和 main 基线后合并，并显式调用现有 `deploy.yml` 部署合并提交。GitHub 的自动令牌对后续工作流触发有限制，显式调度能让发布绑定同一批次。[GitHub 自动触发规则](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)
- 单个来源、模型或文章失败的状态分别回写并退避，保留原来可用的文章。缺少 AI 时仍做采集和已有内容构建、发布。生产冒烟验证本次 SHA、文章与发现文件，失败恢复上一个可用部署，原失败内容进入修复队列。

## 启用前验收

先跑仅读取的首轮，确认博客 RSS、报告、政策和作者站正常提取；在 Actions runner 补验频道 Atom，单一来源失败时仍能产出运行报告。接着用固定证据走通一篇多语市场观察、一篇知识动画商业案例，以及一次已有页实质更新。分别演练重复运行无模型请求和无 PR、来源断开或无 AI 仍盘点、错误收益数字被拦截、单篇失败其余候选继续、main 变化保留人工提交、隔离发布失败恢复。最后核对一次真实 `schedule` 触发和合并 SHA 的线上冒烟。收录、曝光和 AI 引用按 [SEO/GEO 规范](SEO-GEO.md) 单独观察。

本轮已完成设计和公开来源的部分连通性核验。新工作流、采集器、模型、状态分支与定时发布尚未启用。
